## Repository 內可重現的模型測試

在 repository 根目錄執行：

```sh
./rf_midi/tests/run_model_tests.sh
```

測試使用 C11、嚴格編譯警告、AddressSanitizer 與 UndefinedBehaviorSanitizer，涵蓋：

- 全部 **3,184 種設定／2,733,464 個頻點**：首尾頻率、頻率排序、軌內嚴格遞增，以及所有取樣點均落在硬體支援的接收視窗。
- 軌數與點數上下限、非法參數、64-bit 頻率計算。
- 非 1 kHz 的 tick 換算、tick 回繞、掃描時間估計與計時樣本更新。
- 停用軌的 CC 清零遮罩，以及 RSSI 映射、截斷與 NaN 輸入。

成功時會輸出：

```text
PASS model: 3184 configurations, 2733464 frequency samples, timing/limits/masks/RSSI
```

此測試只執行純 C 模型，不會連接 Flipper，也不涵蓋實際 USB、按鍵、螢幕或 RF。

## v0.8 實機觀察

測試直接使用 GitHub Release v0.8 的 `rf_midi.fap`。安裝前保留原 App 備份，僅更新 App；安裝後完整讀回的檔案與公開附件一致。

### 預設設定

新啟動後的 **30 秒**穩定測試段接收到 **129 筆 Channel 1 CC20–CC29**，每個 CC 均有 **12–13 次更新**，值介於 **10–62**；同一 CC 兩次接收的平均間隔約 **2,323 ms**。本段依新啟動預設值推定為 **10 軌 × 50 點**，未透過裝置畫面直接確認設定。CC30–35 的啟動清零發生在此穩定段之前，30 秒區間內未收到這些停用 CC。

### 16 軌 × 200 點與暫停／恢復

使用者在裝置上調整並確認 **Tracks 16／Points 200**。其後的 **60 秒**穩定測試段，主機收到 **72 筆 Channel 1 CC20–CC35**，每個 CC 均有 **4–5 次更新**，值介於 **14–60**；同一 CC 的平均接收間隔介於 **13,407–13,415 ms**。依訊息順序檢查，可辨識 **3 個完整的 CC20 → CC35 掃描輪次**，另有區間邊緣的部分輪次。

使用者亦確認在裝置按下暫停後再恢復；暫停期間，主機的 MIDI 來源維持連線而停止收到 CC。恢復後，同一接收程序再次收到 CC，隨後完成上述 60 秒持續輸出測試。

設定與按鍵操作由使用者現場確認；CC 內容、接收次數與間隔則由主機直接觀測。時間來自主機 MIDI callback 的 monotonic clock，不是裝置畫面的 Last 值，也不是 RF 校準結果。這些特定環境的觀察不能視為固定更新率或量測準確度保證。

### 畫面與正常退出

使用者回報裝置的 **Est／Last／進度條顯示正常**，並以 **Back** 退出。此為現場使用者確認，未提供實際畫面數值，沒有直接擷取 LCD 或比對計時顯示的準確度。

退出時，主機直接收到最後 **16 筆 CC20–CC35，值全部為 0**，隨後 MIDI 來源移除且不再有輸出。USB CDC 控制介面恢復，官方 CLI 可正常回應，App loader 回報沒有執行中的應用程式。退出後再次完整讀回 FAP，仍與公開 v0.8 附件一致。測試結束時裝置停留在正常選單，未再次啟動 App。

過往另做過 128×64 離線畫面檢查，以及模擬 HAL 的操作流程測試。相關輔助程式未隨本 repository 提供；這些歷史結果無法由上面的模型測試指令重現，也不作為硬體驗收依據。
